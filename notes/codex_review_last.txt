## 高危 (High)

### H1. `_do_plugin_check_updates` 每次调用都向同一个 Qt 信号挂新 lambda，从不 disconnect → 内存泄漏 + N 次冗余回调
**位置**: `ui_qt/qt_app.py:4762-4767`

```python
_chk_unreachable = {"n": 0}
try:
    page_plugins.unreachable_reported.connect(
        lambda c: _chk_unreachable.__setitem__("n", int(c or 0)))
except Exception:
    pass
```

`_do_plugin_check_updates` 每次用户点"检查更新"都被调用一次。每次执行都创建一个**新的 lambda** 和**新的 dict** `_chk_unreachable`，lambda 通过闭包捕获本调用局部的 dict。Qt 没有 disconnect，连接累积。

- **症状**：每点 N 次，"检查更新"信号挂 N 个 lambda + N 个 dict。`unreachable_reported` 每次发射时 N 个 lambda 全跑一遍（每次都把同一个 c 写到自己的 dict，多数是无用工作）。dict 和 lambda 随 `page_plugins` 生命周期存活，整个 session 线性增长。
- **验证**：在 `page_plugins.unreachable_reported.connect` 调用前后打印 `len(page_plugins.receivers(page_plugins.unreachable_reported))`，连点 5 次后看是否 = 5。
- **修法**：把 lambda + dict提升到 `__init__`（每个 page_plugins 实例一次），connect 一次；或 connect 后保存 connection 对象，函数入口先 disconnect 上一次的；最简单是用 `QtCore.Qt.UniqueConnection` flag —— 重复 connect 同一定位会被 Qt 忽略。

### H2. `_plugin_queue_identity` 对 `.disabled/` 子目录下的插件 early-return None → API 快路径对禁用插件完全失效
**位置**: `services/plugin_service.py:1518-1521`

```python
plugin_dir = PATHS.plugins_dir(self._comfyui_dir()) / str(name)
if not plugin_dir.is_dir():
    return None
```

`name` 来自 `list_installed()`，可能形如 `Foo@1_2_3`（`.disabled/Foo@1_2_3` 的裸目录名）。`cn_dir / name` 指向不存在的顶层路径，立即 `return None`。

- **后果**：`uninstall`/`disable`/`enable` 对任何 `.disabled/` 下的插件，`_api_try_lifecycle` 都拿 None。`_lifecycle` 的注释写"API 路径未达成终态 → 启动器磁盘执行"，但 `api is None`（前置失败）和 `api is not None`（执行了但 effect 没达成）是不同分支 —— None 路径连"尝试过"的日志都没有，磁盘直连无脑兜底，性能损失（ComfyUI 在跑时本来走 API 几毫秒，现在直接走文件系统）。
- **不是数据丢失**：磁盘直连会正确处理 `.disabled/` 子目录条目（`force_update_selected` 已验证）。但 API 快路径对禁用插件完全失效是事实，与 AGENTS.md "B5：API 先行保留"的方针冲突。
- **修法**：在 `_plugin_queue_identity` 开头先调 `_resolve_plugin_dir(name)` 拿真实路径，不存在才返回 None。

### H3. `_do_plugin_force_update` 没传 `cancel_event`，进度弹窗的"取消"按钮只关弹窗，强制更新继续后台跑**位置**: `ui_qt/qt_app.py:4993-5010`

`_do_plugin_force_update` 调 `_plugin_op_with_progress(...)`，但**没传 `cancel_event`**。弹窗的"取消"按钮只关闭对话框（`pd.is_cancelled()` → `pd.close()`），后台线程里的 `run_force_update` 照常跑 git pull + pip install 直到完成。install/uninstall/disable/enable 也都不传 cancel_event（只有 `_do_plugin_install` 传，见 `:5112-5122`）。

### M2. `_run_cmcli_streaming` 在 proc 10 秒内未退时返回 `returncode=None`，调用方判为"成功"
**位置**: `services/plugin_service.py:1240-1255`

```python
try:
    proc.wait(timeout=10)
except Exception:
    pass
# reader 内如果已经判断过 cancel，再确认一下外层状态。

```

- **场景**：reader thread 因 EOF 退出，但 proc 在 `proc.wait(timeout=10)` 内未结束（极罕见但非不可能：僵尸/未关闭 FD/反病毒扫描）。`proc.returncode` 仍为 `None`，函数返回 `{returncode: None, error: None}`。
- **后果**：`install_streaming` 看到 `rc = res["returncode"]` 是 None，`if rc == 0` 为 False → 走到 `f"cm-cli install 退出码 {rc}"` → "退出码 None"报错。其实更危险的是用户感知"刚刚显示成功"但进程仍在跑（Python 的 `if rc == 0` 把 None 当 False，返回 False 分支，错误提示是给了的；不构成静默成功，但错误信息"退出码 None"很迷惑）。
- **修法**：`if proc.returncode is None` 时主动 `_tree_kill_pid(proc.pid)` + `return {"returncode": -1, ..., "error": "cm-cli 子进程未退出"}`。
